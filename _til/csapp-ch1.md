컴퓨터 시스템 : 하드웨어 + 시스템 소프트웨어  

<h2>컴파일</h2>
<p>: 어떤 언어로 쓰인 프로그램을 다른 언어의 동등한 프로그램으로 번역하는 것</p>  

  - C언어 프로그램을 기계어로 변환하는 과정 소개  
  - 전처리->컴파일->어셈블->링크  
- 다음 hello.c 파일을 기준으로 설명하겠다  

```
    #include <stdio.h>
		int main(){
			printf(“hello, world!\n”);
			return 0;
		}
```
1.  전처리 : .c 소스 텍스트 -> 전처리된 소스 텍스트(.i)  
>><p>- 컴파일 이전의 순수한 텍스트 변환 단계. #으로 시작하는 지시자만 처리</p>
>><p>- #include <>의 경우 해당 헤더 파일의 내용을 그 자리에 통째로 복사 붙여넣기 한다.</p>
>><p>gcc -E hello.c -o hello.i</p>
![전처리](/assets/images/csapp-ch1/hello_i.png)  
>><p>main 함수 위로 헤더 파일의 내용이 들어온 것을 확인할 수 있다.</p>
	
2. 컴파일 : 전처리된 C 코드(.i) -> 어셈블리 텍스트(.s)  
>><p>- 툴체인에서 가장 지능적인 단계이며, 실제로 "언어를 이해"하는 유일한 단계</p>
>><p>- 어휘 분석: 텍스트를 토큰(키워드, 식별자, 연산자, 리터럴)으로 쪼갭니다</p>
>><p>- 구문 분석: 토큰 열을 문법 규칙에 맞춰 트리 구조(AST)로 만듭니다. 문법 오류(세미콜론 누락 등)가 여기서 잡힙니다</p>
>><p>- 의미 분석: 타입 검사, 선언되지 않은 변수 검사 등. int에 포인터를 대입하면 경고가 나오는 단계입니다</p>
>><p>- 최적화: 죽은 코드 제거, 상수 접기(3*4를 컴파일 시점에 12로), 루프 최적화 등</p>
>><p>- 코드 생성: 대상 CPU 아키텍처(x86-64, ARM 등)의 어셈블리 명령으로 변환합니다. 변수를 레지스터에 배치하는 결정도 여기서 합니다.</p>
>><p>gcc -S hello.i -o hello.s</p>
![컴파일](/assets/images/csapp-ch1/hello_s.png)  
>><p>어셈블리 텍스트로 변경된 것을 확인할 수 있다.</p>

3. 어셈블 : 어셈블리 텍스트(.s) -> 오브젝트 파일(.o)  
>><p>- 어셈블리 명령을 기계어 바이트로 바꾸는 거의 1:1 기계적 번역</p>
>><p>- 결과물인 오브젝트 파일은 단순한 기계어 덩어리가 아니라 구조화된 파일</p>
>><p>- 파일을 실행하기 위해서는 호출 함수의 주소와 같은 재배치 정보가 입력되지 않은 미완성의 실행 불가능한 파일</p>
>><p>gcc -c hello.s -o hello.o</p>
![어셈블](/assets/images/csapp-ch1/hello_o.png)  
>><p>어셈블리가 기계어 바이트로 바뀐 것을 확인할 수 있다.</p>

4. 링크 : 오브젝트 파일들(.o)+라이브러리 -> 실행 파일  
>><p>- 여러 오브젝트 파일을 하나로 합치고 어셈블 과정에서 남겨둔 빈칸을 채우는 단계</p>
>><p>gcc hello.o -o hello</p>

>>* 모든 컴파일 과정이 이러한 것은 아니다. 어셈블리로 작성한 코드는 고급 언어를 어셈블리로 변환하는 컴파일까지의 단계는 필요하지 않을 것이고 기계어로 직접 실행 파일을 작성하는 것도 가능하다. 또한 고급 언어라 하더라도 Go, Rus, Java 등에는 독립된 전처리 단계가 없고 Java의 JIT 컴파일과 같이 컴파일 과정이 다른 경우도 있다.  

<h2>명령어 집합 구조(Instruction Set Architecture)</h2>
<p>컴퓨터의 하드웨어와 소프트웨어 간의 인터페이스를 정의하는 개념</p>
<p>기계어를 작성하기 위해 필요한 모든 정보를 말하며 단순히 Instructions의 집합 뿐만 아니라 register, memory, access 등을 포함한 모든 정보를 의미한다.</p>
<p>하나의 표준이 존재하는게 아니라 각 회사가 목표로 하는 설계 철학, 성능 요구 사항, 전력 소비, 응용 분야 등에 따라 다양하게 존재한다.</p>

<h2>프로세스와 쓰레드</h2>
<p>우선 메모리 구조에 대해 이미지로 간략히 확인하고 가겠다.</p>
<h3>메모리 구조</h3>

![메모리 구조](/assets/images/csapp-ch1/process_memory_layout.png)  

- 크게 코드 영역, 데이터 영역, 힙 영역, 스택 영역으로 볼 수 있다.
- 각 영역에 따라 저장하는 데이터가 다르다.

<h3>프로세스</h3>
<p>: 작업의 단위로 실행중인 프로그램</p>
<p>각 프로세스는 자신만의 가상 주소 공간(페이지 테이블), [코드, 전역 변수, 힙] 영역, 열린 파일 디스크립터 테이블, 시그널 핸들러, 현재 작업 디렉터리 등을 갖는다.</p>
<h3>스레드</h3>
<p>: 실행 흐름의 단위로 같은 프로세스의 스레드들은 자원을 공유</p>
<p>각 스레드는 각자 실행을 하기 위해 레지스터 상태, 스택 영역, 스케줄링 상태, errno, TLS 등을 갖는다.</p>
<p>- 파일 디스크립터 테이블, 시그널 핸들러, 스케줄링 상태, errno, TLS 등 익숙하지 않은 개념들에 대해서는 이어지는 챕터들에서 학습할 수 있을 것으로 기대한다.</p>
<p>- 추가적으로 이러한 차이로 인해 발생하는 통신 비용, 컨텍스트 스위칭 비용, 하나의 스레드로 인해 프로세스가 죽는 것에 대한 격리, 각각의 생성 비용 등에 대해서도 차차 다루기로 하자.</p>

<h2>동시성과 병렬성</h2>
<h3>동시성</h3>
<p>- 여러 작업을 다루는 구조로 사람의 멀티태스킹 또는 한 손으로 공 여러개를 돌려가며 던지는 저글링 비유가 적절하다.</p>
<p>- 코어가 1개여도 스케줄러가 짧은 시간 단위로 작업을 교체(컨텍스트 스위칭)하면, 사람 눈에는 A와 B가 동시에 돌아가는 것처럼 보인다.</p>
<h3>병렬성</h3>
<p>- 여러 작업이 물리적으로 같은 순간에 실행되는 상태.</p>
<p>- 병렬성은 물리적으로 실행 단위가 2개 이상 있어야만 가능하다.</p>

![동시성과 병렬성](/assets/images/csapp-ch1/concurrency_vs_parallelism_timeline.png)

<h2>추상화</h2>
<p>복잡한 시스템에서 본질적인 부분만 남기고 세부 사항을 감추는 것</p>
<p>필자가 학습할 때는 세탁기 비유로 학습했는데 이미지는 찾지 못 했지만 적절한 비유라고 생각이 돼서 설명해보겠다.</p>
<p>세탁기를 사용할 때 세탁물을 넣고 버튼만 누르면 세탁이 되고 작업이 끝나면 세탁물을 돌려받는다.</p>
<p>이 때, 내부에서 사람이 들어가서 빨래를 하는지 어떤 식으로 작동하는지는 우리가 알 필요가 없다.</p>
<p>이러한 개념을 사용하는 API, 함수, 네트워크 계층 구조 등 모두 추상화라고 할 수 있고, 앞서 설명한 명령어 집합 구조에서 해당 명세만 따르면 하드웨어와 소프트웨어가 서로에 대해 이해하지 않아도 되는 것 역시 추상화라고 볼 수 있다.</p>
